## When the suite is written
Scope it to the six modules (PRD.md F-01…F-06) plus the SECURITY.md requirements, with these layers:
- **Unit**: `BudgetService` (deposit/withdraw/transfer/delete-both-legs, insufficient funds), `WorkoutReminderStatus::isDue` around hour boundaries, `formatZar`.
- **Integration/Feature**: per-module CRUD through both the web and `api/v1` surfaces; FormRequest validation rules; token issuance and revocation.
- **Tenant isolation**: the highest-value tests. Worth copying fiyobra's `tests/Feature/Security/CrossTenantAccessTest.php` approach — a data-driven sweep over every model-bound route asserting 404 for a non-owner, **plus** its self-auditing test that walks the live route table and fails the build when a new bound route is added without a corresponding isolation case.
- **E2E**: Playwright for the real browser behavior listed as uncovered above.
- **Android**: `BudgetViewModel`/`PomodoroViewModel` state transitions with `kotlinx-coroutines-test` (the countdown's focus→break roll-over is pure logic and worth pinning), `JackApi` decoding against recorded JSON, and `WorkoutReminderWorker` with a fake repository. Prefer hand-written fakes over a mocking framework.
- **Add-on**: the pure helpers first (`format.js`, and `dom.js`'s refusal to accept raw HTML), then `api.js` error extraction against recorded Laravel 422/401 bodies. The parts that actually need a browser — alarms, the service worker, permission flows, history deletion — are the ones no unit test will reach, so they need either a Puppeteer/Playwright run against a loaded unpacked extension or an honest manual checklist.

## What the suite actually pins

**Tenant isolation** (`tests/Feature/Security/CrossTenantAccessTest.php`) — the highest-value file. All 68 model-bound web and API routes are swept (33 before issue #4, 35 added by it): a non-owner must get 404, never 403. Three guards stop it passing for the wrong reason, which the earlier manual check did once when no record id parsed and every request 404'd trivially:
1. the fixture asserts each record exists and belongs to the victim before any request;
2. a paired test asserts the **owner** does *not* get 404 on the same route, so a broken route or failing validation cannot masquerade as isolation;
3. write payloads are valid, because a 422 would be returned before the ownership check runs.

A route-table audit fails the build when a model-bound route is added without a case, so the sweep cannot fall behind the router.

**One caveat on that audit, found while adding issue #4's routes.** It only sees route parameters it already has a fixture for, because `isTenantOwnedRoute()` matches against the fixture keys. Thirty-five new bound routes were therefore invisible to it until the fixtures were added — the build stayed green while nothing checked them. Adding the fixture is what switches the check on, so that is the step to remember, not the endpoint list. CODE_STYLE.md's review checklist now says so.

Two further things issue #4 forced on that file. `exercise` is a user-owned exercise rather than a catalog one, because a catalog exercise is readable by everybody by design and using one would have asserted the opposite of the rule. And the set-logging payloads name a *shared* catalog exercise: pointing them at the victim's own would have made the attacker's request fail validation with a 422 before the session's ownership check ever ran, so the test would have passed without proving anything.

**Money** (`tests/Unit/BudgetServiceTest.php`) — deposits, withdrawals, the exact-balance edge, refused overdrafts leaving the ledger untouched, transfers writing both legs under one group or neither, deleting one leg removing its counterpart. It also asserts `balancesFor()` issues **exactly one query**, so the no-N+1 claim is verified rather than asserted.

**Reminder boundary** (`tests/Unit/WorkoutReminderStatusTest.php`) — "due" means nothing logged since the top of the hour; 10:59 does not count for an 11:30 now, 11:00 does. Since issue #4 a logged set or a finished session counts too, which `WorkoutPagesTest` pins: nudging somebody who has just finished a tracked workout would be the app asserting something the user knows to be false.

**Personal records and the shared rules** — the arithmetic behind a personal best exists in four places, so it is asserted in four places against *the same vectors*: `tests/Feature/Services/WorkoutRecordsTest.php`, `laravel/resources/js/Lib/workoutProgress.test.js`, `extension/tests/workoutProgress.test.js` and `android/.../workout/WorkoutProgressTest.kt`. Change one copy of the rules alone and three test files fail, rather than the surfaces quietly telling the user different things on different devices. The vectors worth knowing: a single rep is its own one-rep max (Epley would inflate it), 62.5 kg × 5 estimates 72 917 g, a warm-up is never a record, and a measure the set does not carry is ignored rather than counted as a loss — so a rep PR at a lighter load still counts.

**Training volume and streaks** (`tests/Feature/Services/WorkoutAnalyticsTest.php`) — bucketing in the caller's timezone (an evening set in Johannesburg belongs to that day, not the previous UTC one), an untrained *today* leaving yesterday's streak standing because the day is not over, a gap ending it, the longest streak surviving the current one breaking, and the calendar keeping its empty days because the gaps are the point of a consistency view.

**The upload** (`tests/Feature/Api/ProgressPhotoTest.php`) — written against the ways a progress photo could leak rather than the happy path alone: the file lands on the private disk, the stored name is random with the extension taken from the *validated* mime type (so `selfie.php.jpg` cannot become a `.php` path), a PHP file renamed `.jpg` is refused by content sniffing, a non-owner gets 404, a signed-out visitor gets 401, the response carries `nosniff` and `Cache-Control: private`, and deleting the row deletes the file. The sniffing test deliberately uses a real temp file rather than `UploadedFile::fake()`, which reports its mime type from the filename and would have proved nothing.

**Three bugs these tests found**, all of which would have shipped: a freshly created `WorkoutSet` had no `is_warmup` attribute in memory, so the record check crashed on the one instance it is handed straight after a write; a `date` cast serialises as a full datetime, so the body-metric "one reading a day" lookup never matched and the upsert hit the unique index instead of updating; and a cue the user left blank arrives as null through `ConvertEmptyStringsToNull`, which the validation rejected rather than dropping.

**Prune** (`tests/Feature/Console/PruneHistoryEntriesTest.php`) — the cut-off is respected either side of the window, `--days` overrides it, a window below one day is refused rather than deleting everything, the job is system-wide, and it is still registered on the daily schedule.

**API contract** (`tests/Feature/Api/ApiContractTest.php`) — the shapes both clients decode: token issue/revoke, identical wording for a wrong password and an unknown address, `balance_cents` + `meta.currency`, `"125.50"` → `12550` with no float drift, overdraft and same-account transfers refused, per-user unique account names, `workout-entries/due` not shadowed by the show route, `meta.retention_days`, history being immutable, and `user_id` being unsettable from the body.

**Android** — the transfer-direction rule that was actually wrong in the first build (both legs must read source → destination), type classification, and clock formatting including the negative case.

**Android ViewModels** — now testable because the five module repositories were extracted into interfaces (`NotesRepository` and friends are interfaces; `ApiNotesRepository` is the only production implementation). `BudgetViewModelTest` covers the submit flow — a rejected write keeps the composer open with the server's reason, a partial load failure keeps the balances already on screen rather than blanking them, and the typed amount string reaches the repository untouched.

**`PomodoroTimerEngineTest`** — the countdown itself, on virtual time: ticking, focus rolling into the break, a no-break preset ending after focus, pause freezing the clock, resume continuing from where it stopped, restart and skip in every phase/running combination, and `stopIfPreset` leaving an unrelated running timer alone. Issue #3 changed one of these with the behaviour it covers: a finished break used to end the session and now loads the next focus run and waits, since `auto_start_focus` defaults to off. A trap worth knowing about if more are added — a preset that auto-starts in both directions never stops on its own, and `runTest` drains the scheduler before it returns, so such a test must stop the engine itself or it hangs the suite rather than failing it; the `@After` teardown runs too late. This moved out of `PomodoroViewModel` into a process-wide `PomodoroTimerEngine` so the welcome page and the Pomodoro screen share one running timer instead of each keeping its own (starting one and finding it "stopped" on the other screen was a real bug this fixed) — and the engine is deliberately Context-free so it stays unit-testable without Robolectric; `JackApplication` is what notices the engine going active and starts the foreground notification service for it. `PomodoroViewModelTest` and `DashboardViewModelTest` now only cover what is actually theirs: preset CRUD, the reminder/workout flow, and that each ViewModel's `state` correctly mirrors the shared engine.

**The Pomodoro cycle, asserted three times on purpose.** `pomodoroCycle.test.js` (web), `PomodoroCycleTest.kt` (Android) and `extension/tests/pomodoroCycle.test.js` run the *same* cases against three separate implementations of the same rules — most pointedly a full eight-phase sequence that has to come out short, short, short, long. The duplication is the point: ARCHITECTURE.md records that these three files must agree, and three suites asserting one sequence is what turns a divergence into a failing build rather than into a user noticing their phone and their browser disagreeing about when the long break falls. Each also pins the auto-start defaults (a break begins on its own; going back to work is your decision) and the wire names the server validates.

**`PomodoroAnalyticsTest`** — where nearly all this module's arithmetic lives, and the timezone cases carry the most weight. The service buckets in whatever zone the caller names rather than the app's UTC, so the file pins the case that makes that necessary: 22:30 UTC is already tomorrow in Johannesburg, and the same instant has to file under a different day for each caller. That property looks correct on a developer machine in UTC+2 whether or not the conversion is really there, which is exactly why it is asserted rather than eyeballed. Also: empty days kept in the chart rather than dropped (dropping them misreads as a streak), a day still in progress not breaking yesterday's streak, a completion rate of `null` rather than `0%` before anything has been started, and the most productive hour being the one with the most *time* rather than the most sessions.

**`PomodoroPresetContractTest`** — chiefly the compatibility case. A preset went from four fields to fourteen, and an Android build or an add-on copy that has not been updated still posts the old four; every added column has a default behind it so that keeps working, and this is what proves it rather than assuming it.

**`PomodoroSessionContractTest`** — the bounds on a client-supplied timestamp. Clients send their own times because they can be offline when an interval ends, which is a deliberate loosening, so the guards around it are pinned: nothing finishes in the future, a couple of minutes of ordinary clock skew is tolerated rather than thrown away, and a session cannot be attributed to another user's preset.

**`PomodoroPagesTest`** — prop-name tests, which usually earn little. They earn their place here because the module is four pages sharing a timer, a session log and a partial reload keyed by page name: a prop renamed on the server with the page left alone fails silently in the browser, the figure simply stopping. It also pins the loading contract — opening Presets must run no analytics query — and that logging an interval answers 204 rather than redirecting, since a redirect would yank the user onto the Pomodoro page whenever a timer finished while they were reading their notes.

**`PomodoroSessionRecorderTest`** — the five-second floor below which a phase change was a misclick rather than a session, that an abandoned interval is still recorded (as abandoned), and that an unreachable server loses the row rather than taking the timer down with it.

**`AppUpdateCheckerTest`** — version-string comparison (`"0.1.10"` reading as newer than `"0.1.9"`, not the other way around as plain strings would have it) and parsing GitHub's "latest release" response, including a malformed or incomplete body degrading to "no update" rather than crashing on launch. The network call itself is untested, consistent with the rest of this app's HTTP-calling code.

**Sign-in** (`LoginViewModelTest`) — `AuthStore` is an interface too (`ApiAuthStore` is the implementation), so the screen is testable without a server or a keystore. Covered: the submit button needing both fields, the email being trimmed, the **server address being applied before the request** rather than after (otherwise a corrected address always fails on the first try), a rejected sign-in reporting the reason and leaving the form usable, typing clearing the previous error, and a double tap sending only once.

**The remaining three ViewModels** — Notes (create vs. update chosen by a blank id, title trimmed, blank title refused with the editor left open), Clipboard (the device stamp always recorded, a blank title sent as `null`, and content kept **verbatim** including leading whitespace, since snippets are often code or keys that trimming would corrupt), and Workout (logging clearing the nudge, and a failing reminder check not taking the entry list down with it — the banner is a nicety, the entries are the point).

A pattern worth keeping: each of these asserts that a rejected write leaves the form open carrying the server's reason. That is the behaviour a user actually notices, and the easiest to break.

Fakes are hand-written (`app/src/test/.../testing/Fakes.kt`), not generated: they are short and they break loudly when an interface changes.

**Add-on** — URL joining with and without a trailing slash, bearer header presence, the first-field-error-wins rule for a 422, an unreachable server reported as such, a 401 clearing the session while other failures do not, and history leaving the retention window `null` rather than guessing one. `pomodoro.test.js` covers the pure `restartPatch`/`skipPatch` functions the popup's Restart and Skip buttons use — pulled out of the `chrome.storage`/alarm side effects specifically so this logic is testable without a browser. Since issue #3 those two run on the shared cycle in `lib/pomodoroCycle.js`, so these cases also pin the long break landing on the fourth focus run and the set resetting after it.

## Known gaps
- **Coverage is unmeasured** (no driver installed).
- **The Pomodoro's generated audio is untested and unheard.** `ToneSynth`/`PomodoroSounds` on Android and `Lib/audio/` on the web synthesise every alarm, tick and ambience bed; none of it has been played on a real device or in a browser, and nothing asserts what comes out. Unit tests would only prove the graph was built, which is not the question — the question is whether a chime sounds like a chime. This needs listening to, by hand, on each surface.
- **Strict mode's privileged halves are unexercised.** Android's `FocusGuard` needs `ACCESS_NOTIFICATION_POLICY` granted in Settings and a real `NotificationManager`, so neither the silencing nor the restore-the-previous-filter path has run. The add-on's `declarativeNetRequest` blocking has never run either — it inherits the existing gap that the extension has never been loaded as a real extension. Both are written to degrade to "asked for but not allowed" and say so in the UI, which is itself untested.
- **Session logging is unit-tested everywhere but has only been run end to end on the web**, where a real start-then-skip in a browser produced `POST /pomodoro/sessions → 204` followed by the partial analytics reload. `PomodoroSessionRecorderTest` covers the Android recorder's own decisions against a fake repository, but no interval has been logged from an actual device, and the add-on's background logging — which happens inside the service worker — is still unreached for the same reason the rest of that host is.
- Android **Compose UI** is untested — the ViewModels are covered, but nothing asserts a screen renders their state. That needs instrumented or Robolectric tests. Issue #4 added five more screens under this gap, including the one that picks a progress photo: `PickVisualMedia`, the content-resolver read and the mime check in front of it have never run.
- **Issue #5's Android planning surface is online-only by design** - categories, limits, goals, reports, due state and receipts are fetched through the API and never served from a local cache, so there is nothing offline to test beyond the ledger queue, which keeps its tests.
- **Tracked workouts do not work offline on Android**, and that is a deliberate limit rather than an untested one. `ExerciseRepository`, `TrainingRepository` and `BodyRepository` have no local, signed-out half and no outbox: the exercise catalog is server-seeded reference data, and a set queued offline belongs to a session that may not exist on the server yet, so `OutboxDrainer` would need session-id remapping before any of it could replay. A photo upload is not queued either — queueing one would mean copying the image into the app's own storage, leaving a copy of somebody's body photo on the device. The one-line entry log keeps its offline queue and its tests. PRD.md carries the open decision.
- **The rest timer's platform half is unexercised.** `WorkoutRestTimer` itself is covered under a controlled clock, but `WorkoutRestService` — the foreground notification, its two actions, and the `specialUse` service type — has never run, like `PomodoroTimerService` before it. The add-on's rest alarm is in the same position for the same reason as everything else in that host.
- **Nothing on Android has run on a device or an emulator since issue #4.** `assembleDebug` is clean and the unit tests pass; the five new screens have not been looked at.
- **`extension/src/lib/dom.js` is untested** — every function touches `document`, so it needs jsdom or a browser runner.
- **The extension host is still unexercised**: service worker, `chrome.alarms`, notifications, permission prompts, `history.onVisited` and the auto-delete path. No unit test reaches these; they need Playwright against a loaded unpacked extension, or a manual checklist.
- **No E2E anywhere.** The web app has never been clicked through in a browser; Android was exercised by hand on an emulator but has no instrumented tests; the add-on's popup was driven only through an API-stubbing harness.
- The hourly reminder has never been observed firing on any client (one-hour periods).
