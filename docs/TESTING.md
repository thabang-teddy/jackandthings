# Testing

## Current state
**No automated test suite has been written for this project, and none has been run.** Testing was deferred while implementation was in flight (owner's standing rule). All three surfaces — server + web, Android, and the browser add-on — now exist, so writing the suite is the next piece of work rather than a future one.

What exists in `laravel/tests/` was generated by the Breeze starter kit, not written for this project:
`tests/Feature/Auth/*` (registration, authentication, password reset/update/confirmation, email verification), `tests/Feature/ProfileTest.php`, `tests/Feature/ExampleTest.php`, `tests/Unit/ExampleTest.php`, `tests/TestCase.php`.

**These have never been executed here.** Their status is *Not run* — not passing, not failing. PHPUnit 12.5 is installed as a dev dependency; Pest is not installed. (fiyobra uses Pest + Playwright, which would be the natural choice when a real suite is written.)

**Not verified, and the gap is significant:** the extension has never been loaded as an actual extension. Chrome 156 refuses the `--load-extension` command-line switch, and loading from `chrome://extensions` needs a native file dialog that cannot be driven here. So the manifest has never been accepted by a browser, and **the service worker, `chrome.alarms`, notifications, the real permission prompts, `history.onVisited` recording and the auto-delete path are all unexercised**. The harness proves the views and the API client; it proves nothing about the extension host. Load it by hand (see ARCHITECTURE.md "Operations") before trusting any of it.

Also still uncovered: the web app in a real browser (clicks, the countdown advancing, `navigator.clipboard`, dark mode, responsive layouts); on Android, the hourly reminder actually firing (a one-hour WorkManager period — never observed), the share-sheet path, permission refusal, rotation, offline behaviour, and real hardware; and concurrency on transfers.

## When the suite is written
Scope it to the six modules (PRD.md F-01…F-06) plus the SECURITY.md requirements, with these layers:
- **Unit**: `BudgetService` (deposit/withdraw/transfer/delete-both-legs, insufficient funds), `WorkoutReminderStatus::isDue` around hour boundaries, `formatZar`.
- **Integration/Feature**: per-module CRUD through both the web and `api/v1` surfaces; FormRequest validation rules; token issuance and revocation.
- **Tenant isolation**: the highest-value tests. Worth copying fiyobra's `tests/Feature/Security/CrossTenantAccessTest.php` approach — a data-driven sweep over every model-bound route asserting 404 for a non-owner, **plus** its self-auditing test that walks the live route table and fails the build when a new bound route is added without a corresponding isolation case.
- **E2E**: Playwright for the real browser behavior listed as uncovered above.
- **Android**: `BudgetViewModel`/`PomodoroViewModel` state transitions with `kotlinx-coroutines-test` (the countdown's focus→break roll-over is pure logic and worth pinning), `JackApi` decoding against recorded JSON, and `WorkoutReminderWorker` with a fake repository. Prefer hand-written fakes over a mocking framework.
- **Add-on**: the pure helpers first (`format.js`, and `dom.js`'s refusal to accept raw HTML), then `api.js` error extraction against recorded Laravel 422/401 bodies. The parts that actually need a browser — alarms, the service worker, permission flows, history deletion — are the ones no unit test will reach, so they need either a Puppeteer/Playwright run against a loaded unpacked extension or an honest manual checklist.
